# Pre-1.0 whole-codebase review (2026-10-17)

18 parallel read-only reviewers + 1 tooling pass over all four tiers (~135k lines):
central (2: concurrency, auth/SQL), community (5: main.cpp in three slices, DB/search/authz,
attachment HTTP), native Rust (5: net/commands, E2EE, voice/audio, Linux capture/encode, video
receive + Windows), renderer (4: chat, stores/voice/call, servers/channels/search,
settings/DMs/components), Electron main + hotkeys, and a cross-tier wire-contract pass. Every
reviewer was given CLAUDE.md's standing decisions and told to drop anything it couldn't trace.
Findings marked **✔** were re-read in the code by the lead after the reports came back;
**×N** means N reviewers found it independently. Severity is the reviewer's, adjusted where
duplicates disagreed. The review itself changed no code; the fixes that followed are listed under "Fix status".

## 2. Cross-cutting themes

1. **Forwarding client packets wholesale.** S1 (central DM/call), S2 (community CHANNEL_MSG), DM `reply_to_*` forwarded unchecked when `reply_to` is 0/invalid (central `main.cpp:552`). Rule to adopt: every server → client message is built from a field whitelist; a unit/e2e test asserts relayed packets carry no `auth_token` and no unknown fields.
2. **Server responses vs the client's 2 MiB frame cap** (A1). Every list/page response needs a byte budget, every client string a cap. Also reconsider the client side: an oversized frame could be read and discarded instead of killing the connection.
3. **Silent drops vs answered refusals** (B13, plus oversized CHANNEL_MSG / unknown channel / self-DM / oversized envelope all `return` with no reply → pending bubble until the 30 s watchdog and the text is not restored; START_STREAM over the per-channel cap; MEMBER_SEARCH/AUDIT_LOG/MEMBER_LIST show "server may be an older version"). 4. **Count-capped queues** (S17; also native TSFN main bus and thumbnail bus are unbounded, MLS driver queue unbounded — `events.rs:27-37, 338`, `e2ee/group.rs:146`).
5. **Blocking work on the community's single io thread** (it also relays voice): channel delete/wipe and retention sweeps (one transaction, per-row FTS triggers, 6 `remove()` per attachment — 7 copy-pasted unlink lists, two missing `.partial`), attachment file I/O (256 KB `fread`/`fwrite`/`fflush`, `filesystem::space`), permission-cache rebuild after any layout change (online users × channels × 3 SQL each, `visible_channels` re-runs `list_channels()` per recipient), CHANNEL_KEYS_REQ (all members + up to 1000 queries), member list/search pages (load + sort the whole roster per page), `SESSION_TOKEN_UPDATE` before the rate limiter (Ed25519 verify + PEM re-parse + UPDATE per packet, replayable). Chunk deletes across posted turns, unlink on a worker, cache the sorted roster by `roster_revision_`.
6. **Reconnect and resync.** B3, B4, plus: every central LoginRes (resumes included) tears down and reconnects every community (known CL3 — now worse, since resume tokens make central restarts routine: users × communities reconnects at once); a community down at login is never retried and CERT_MISMATCH from auto-rejoin/reconnect is only logged (prompt never shows); any refused auto-rejoin drops the central membership regardless of `errorCode` (a 1 s clock skew at a community = "Membership revoked" for everyone, since `verify_token` has zero `iat` leeway); TCP connect / TLS handshake have no timeout (127 s or forever); a slow auto-rejoin connect can land in the *next* account's state after logout/login; Postgres restart: stale pooled connections fail once and DB errors read as "wrong password" (counted as failed sign-ins) and resume falls back to bcrypt; the stale sweep kills logins queued for bcrypt > 60 s (livelock above ~720 queued logins — this deploy, since no client has a resume token yet).

8. **UI permission checks that disagree with the server.** Delete-others uses server-wide MANAGE_MESSAGES (server checks per channel); role editor enables bits the actor lacks and offers roles with bits the actor lacks; channel reorder sends only visible channels but the server requires the full set (×2); rows look draggable with per-channel MANAGE_ROLES but drag needs MANAGE_CHANNELS; paste/drop ignore ATTACH_FILES.

## 3. Medium findings by tier

### Central (`src/server/`)
- **2 MiB allocated per frame before sign-in** (`main.cpp:262-268`, ×2): header alone → zero-filled 2 MiB, held 60 s; 256 conns × 2 MiB per address. Community has `kPreAuthMaxFrame = 64 KiB` — do the same.
- **Profile read error signs the user in as visible** (`auth_manager.cpp:1301`, `main.cpp:1697-1710`): `getPresenceProfile` defaults (online, friends-only off) on failure → an invisible user announced online. Return optional; refuse login.
- **Bundle + backup publish not atomic** (`main.cpp:1025-1041`): bundle commits, backup in a second transaction; on backup failure peers already seal to a key with no backup.
- **Unlimited key publishing** (`main.cpp:972`): ~432k new `e2ee_keys` rows/connection/day, each pushing E2EE_KEYS_CHANGED to all watchers. Per-account daily cap.
- **4–6 transactions per DM** (×2): `resolveUser`/`isBlocked`/`getDmFriendsOnly`/`areFriends`/`fetchDmPreview` each a `pqxx::work` (BEGIN…ROLLBACK), no prepared statements, ~9–18 round trips. `nontransaction` for reads; one CTE.
- **Shared-secret packets allow unlimited guessing** (`main.cpp:1455-1550`): bad secret → log + keep reading. Close + per-address bucket.
- **Presence subscription churn monopolises the directory mutex** (`main.cpp:2077-2145`): each subscribe can swap 5,000 uids + build/serialise the answer under the one lock (~2 ms × 2/s/connection). Cap newly added uids per window.
- **Presence updates delivered after the lock is released** (`main.cpp:2073, 1956-1961, 2006`): offline/online reorder → ghost-online. `deliver_all` under the lock (it only posts).
- **Rename holds `FOR UPDATE` across bcrypt** (`auth_manager.cpp:628-638`, ×2): stalls the user's DM/friendship FK checks ~250 ms on DB threads.
- **TLS 1.3 disabled everywhere** (`ssl::context::tlsv12` pins min *and* max to 1.2 — central `main.cpp:2289`, community `:6319`, community→central `:6136`; ×3). Use `tls_server`/`tls_client` + `no_tlsv1/1_1`.
- **No TCP_NODELAY** anywhere (central, community, client): back-to-back small frames wait on delayed ACK (40–200 ms).
- **Avatar amplification** (`main.cpp:1273/1298`): 1 MB cap (comment says 200 KB), 1 change/s, each push makes every watcher refetch.

### Community (`src/community/`)
- **Timeout / server mute / deafen wiped by leave + rejoin** ✔ (`db.cpp:1510-1536`): they live on the deletable `members` row; LEAVE isn't timeout-gated; any live invite re-adds a clean row. Keep moderation state in a uid table that survives leaving.
- **Transferred owner keeps their timeout / server mute forever** (`main.cpp:3690-3718`, `db.cpp:1349`): nobody can clear them (owner target refused), relay has no owner bypass.

- **Any member can force a streamer to 4 IDR/s** (`main.cpp:6556-6577`): KEYFRAME_REQUEST only checks the requester's key exists, not that they watch / can VIEW; streamer has no local throttle. P2P path has no throttle at all.

- **Reorder rejected for managers without VIEW on every channel** (`db.cpp:2892`, ×2) and each failure `broadcast_channels()` to everyone.

- **Invites unbounded** (×3): CREATE_INVITE on by default, no per-creator cap, expired rows never swept, `INVITE_LIST` loads all (A1), `INVITE_REVOKE` scans all, each create = a central TLS job on the 4096-slot queue shared with heartbeats.

- **Full message text logged to journald** (`main.cpp:1988-1993`, ×2) — outlives deletes, wipes and retention; invite codes logged too.
- **Search monopolised by one member** (`search.cpp:302-318`): supersede per session, 8 sessions × 3 s broad searches fill the 32-slot FIFO.
- **Multi-author search sorts every matching row** (`search.cpp:461-465`): `IN (…) ORDER BY id DESC` → temp B-tree; measured 142 ms vs 0.3 ms with `UNION ALL` arms.
- **Retention sweep unbounded on the io thread** (`main.cpp:5263-5392`, `db.cpp:4265-4328`); `prune_text_messages` / `delete_messages_by_sender_since` ignore `step()`/COMMIT results and still unlink + broadcast.

- **Role assignment has no target-hierarchy check** (`main.cpp:2991-3040` vs `authz.hpp:87` comment and v3 table) — owner decision needed.
